# Contributor activation sequence

## Goal

Help a first-time contributor move from repository comprehension to one useful, credited merge without requiring production access or broad architecture knowledge.

## Sequence

1. **Welcome:** Point to the 60-second demo, package map, code of conduct, safety model, and eight `good first issue` briefs.
2. **Choose:** Match interest to a pack, fixture, reporter accessibility, redaction test, generated-selector test, or documentation task.
3. **Claim:** Confirm scope publicly in the issue and identify a mentor plus first checkpoint.
4. **First proof:** Ask for one failing test, invalid pack example, or documentation reproduction before polish.
5. **Draft:** Open a draft pull request with user pain, evidence, safety/privacy, tests, and non-goals.
6. **Review:** Respond with required changes separated from preferences; preserve the issue boundary.
7. **Merge and credit:** Explain where the change appears, credit the preferred identity in release notes and pack attribution, and invite one next contribution without pressure.
8. **Learn:** Ask what slowed the contributor down and update mentorship or issue templates based on repeated evidence.

## Maintainer service levels

Do not promise a fixed response time before maintainer capacity is known. Each mentored issue should state the current expected review window when assigned. If capacity changes, release the issue promptly rather than leaving a contributor blocked.

## First cohort

Invite up to five contributors across code, accessibility, packs, and documentation. Track time to first checkpoint, scope changes requested, review rounds, validation failures, merge outcome, and whether the contributor returns. Do not rank contributors by raw activity.
