# HumanQA v0.1 launch plan

## Launch objective

Recruit 10 qualified users to run one authorized local or staging journey and learn whether the evidence bundle changes a real release, debugging, accessibility, or test-authoring workflow. Stars and impressions are secondary distribution signals, not proof of value.

## Positioning

**Evidence-first product quality checks for web apps.** One declared journey produces browser evidence, deterministic UX/accessibility findings, a transparent release verdict, and a safe Playwright scaffold. No model key, hosted account, or artifact upload is required.

Avoid “AI replaces QA,” “automatic UX research,” “WCAG compliant,” “production safe,” and “find every bug.” Say exactly which declared state was exercised and what evidence exists.

## Readiness checklist

- Fresh-install quick start passes on at least Linux and Windows or documented limitations are visible.
- Broken and fixed fixture runs are deterministic.
- README hero passes a 10-second comprehension check.
- Fixture-only screenshots and GIF are sanitized.
- All six quality commands pass.
- Security advisory, issue forms, Discussions, roadmap, and contribution guide are enabled.
- npm and GitHub release notes match the changelog.
- No badge, post, image, or directory copy implies unverified adoption or benchmarks.

## Launch sequence

### Phase 1 — private usability trials

Run three observed sessions: one startup engineer, one QA engineer, and one accessibility practitioner. Fix only setup blockers, unsafe defaults, misleading claims, and reproducible report confusion.

### Phase 2 — first 10 users

Recruit through direct, context-rich invitations. Offer a 30-minute “bring one journey” session. Record explicit consent, setup time, first-audit success, disputed findings, evidence opened, and artifacts adopted.

### Phase 3 — public repository launch

Publish one 60-second fixture demo, a sanitized static report, a short technical architecture post, and two contribution issues. Distribute to relevant Playwright, QA, accessibility, developer-tool, product-engineering, and coding-agent communities while respecting self-promotion rules.

### Phase 4 — Product Hunt only after onboarding evidence

Do not schedule Product Hunt until at least five independent first audits succeed. Product Hunt is a concentrated feedback event, not the validation itself.

## Product Hunt outline

- **Name:** HumanQA
- **Tagline:** Evidence-first product quality checks for declared web journeys.
- **Thumbnail:** HumanQA wordmark plus evidence-chain mark; no user-count badge.
- **Gallery:** terminal command, report verdict, expanded finding, generated Playwright test, pack YAML, privacy/safety panel.
- **Demo:** 60-second broken → evidence → scaffold → fixed narrative using only the local fixture.
- **Maker comment:** Explain the evidence gap between product requirements, Playwright, axe, and release decisions; state what v0.1 deliberately does not do; invite one real journey and pack contributions.
- **First comment question:** “What is the last web journey you had to prove before release, and which evidence did you assemble manually?”
- **FAQ:** Why declared journeys, why no required AI, how safe mode works, accessibility limitations, data handling, and how this differs from plain Playwright.
- **Day-of response:** Answer evidence and safety questions first. Log requests by job, not vote count. Never offer a testimonial prompt.

## Success signals

Use the thresholds in `docs/discovery/03-validation-plan.md`. The launch earns continued investment when users complete audits, understand evidence, adopt an artifact, and return. A large view or star count without first successful audits is a distribution signal only.

## Rollback and stop conditions

Pause promotion for a secret leak, unsafe action, corrupt trace, materially misleading report, or reproducible false release block. Publish a transparent fix note. Stop expansion if first-10-user thresholds meet the documented STOP conditions after one focused correction.
