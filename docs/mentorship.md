# Mentorship-friendly contribution guide

Issues labeled `mentor available` are designed for a contributor who may be new to this repository, open source, QA automation, or accessibility engineering.

## Contributor flow

1. Comment on the issue with the part you want to attempt and any access needs.
2. A maintainer confirms scope, points to one starting file and one relevant test, and names the first checkpoint.
3. Open a draft pull request after the smallest observable change.
4. Ask questions in the issue or draft. There is no penalty for returning an issue to the pool.
5. Run only the relevant check while iterating, then the complete required suite before review.

## Mentor responsibilities

- Explain the user pain and evidence standard, not dictate every line.
- Keep the issue bounded and defend its non-goals.
- Provide synthetic fixtures and never request production access.
- Review the first checkpoint before the contributor invests in polish.
- Give actionable feedback with examples and distinguish required changes from preferences.
- Credit research, testing, documentation, and design work alongside code.

## Good first contributions

Pack additions, fixture twins, reporter accessibility, error-message improvements, platform quick-start validation, documentation examples, and narrowly specified rule tests are preferred. External integrations, authentication, browser safety policy, scoring changes, and model adapters require closer maintainer involvement.

## Accessibility

Ask for the communication and review format that works for you. Maintainers should provide text alternatives for visual evidence, avoid color-only feedback, keep issue structure consistent, and accept asynchronous participation.
